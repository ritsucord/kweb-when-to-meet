# 프론트엔드 구현 시 알아둘 점

`src/schemas.ts`의 JSDoc이 엔드포인트별 명세다. 이 문서는 **명세에 적히지 않았지만 서버가 실제로 그렇게 동작하는 것**과, 구현할 때 부딪히기 쉬운 부분을 모았다. 명세와 다른 내용은 없고, 명세가 정하지 않은 부분만 다룬다. 서버 동작은 `backend/src/api.test.ts`가 실제 HTTP로 검증한다.

## 1. 연결

- 모든 경로는 `/api` 아래다. 명세의 경로(`/sessions` 등)에 `/api`를 붙인다.
- **서버에 CORS 설정이 없다.** 개발 중에는 Vite 프록시로 같은 출처처럼 쓴다. (백엔드 기본 포트는 3000)
  ```ts
  // frontend/vite.config.ts
  server: { proxy: { '/api': 'http://localhost:3000' } }
  ```
- 배포도 같은 출처(리버스 프록시)를 전제한다. 출처가 갈라지면 CORS와 쿠키의 `SameSite` 정책을 서버에서 바꿔야 한다.
- 변경 요청(POST, PATCH, DELETE)은 JSON 본문이면 `content-type: application/json`을 붙인다. 본문이 없는 요청은 본문을 보내지 않는다.
- 클라이언트 생성은 `contract`를 `OpenAPILink`에 넘기는 방식을 염두에 두고 만들었다. 아래는 서버와 함께 확인하지는 않은 스케치다.
  ```ts
  const link = new OpenAPILink(contract, {
      url: `${location.origin}/api`,
      fetch: (input, init) => fetch(input, { ...init, credentials: 'include' }),
  })
  ```

## 2. 인증

- 로그인(`POST /sessions`)이 성공하면 서버가 **`session` 쿠키**를 심는다. 이후 요청은 브라우저가 알아서 쿠키를 보낸다.
  - 쿠키는 `HttpOnly`이므로 JS에서 읽을 수 없고, 읽을 필요도 없다. `Secure`는 운영(`NODE_ENV=production`)에서만 붙는다.
  - `fetch`는 같은 출처면 기본으로 쿠키를 보낸다. 다른 출처로 보낼 일이 생기면 `credentials: 'include'`가 필요하다.
- `Authorization: Bearer <토큰>` 헤더로도 인증된다. 쿠키를 쓸 수 없는 환경(앱, 테스트)용이다. 토큰은 쿠키 값과 같다.
- **응답의 `sessionId`는 토큰이 아니다.** 공개 식별자라서 `DELETE /sessions/{sessionId}`에만 쓴다. 인증에는 쓸 수 없다.
- 세션은 로그인 후 **14일** 동안 유효하고, 사용해도 연장되지 않는다. 만료되면 보호된 모든 엔드포인트가 401이다.
- 로그인 상태 복원은 새로고침 시 `GET /sessions/current`로 한다. 401이면 로그아웃 상태다.
- **어떤 보호된 요청이든 401이 오면** 로그인 화면으로 보내는 공통 처리를 두는 것이 좋다.
- 세션 목록을 주는 엔드포인트는 없다. 다른 기기 로그아웃은 로그인 때 받은 `sessionId`를 저장해 둔 경우에만 쓸 수 있다.
- 로그인 실패는 이메일이 없는 경우와 비밀번호가 틀린 경우 모두 같은 401이다. 화면 문구도 구분하지 않는다.
- 비밀번호를 바꾸는 API는 아직 없다. (서버 내부에는 있다. 바꾸면 다른 기기의 세션이 모두 끝나는 정책이다)

## 3. 오류 응답

- 모든 오류 본문은 `DefaultErrorResponse` 형태인 `{ "code": 403, "msg": "..." }`이고, `code`는 HTTP 상태와 같다. 경로가 없을 때(404)도 같다.
- **`msg`는 개발자용 영어 문장이다.** 사용자에게 그대로 보여주지 말고 `code`로 문구를 정한다.
- 형식이 틀려 400이 되는 경우 `msg`는 항상 `"Input validation failed"`이고 **어느 필드가 틀렸는지는 알려주지 않는다.** (참여자가 멤버가 아닌 경우처럼 서버 규칙 때문에 나는 400은 다른 `msg`가 온다) 서버에 보내기 전에 `shared`의 zod 스키마로 먼저 검증하면 필드별 오류를 보여줄 수 있다.
  ```ts
  import { CreateUserRequest } from 'shared'
  const result = CreateUserRequest.safeParse(form)   // 실패하면 result.error.issues에 필드별 사유
  ```
- 상태 코드의 의미는 명세의 `@throws`를 따른다. 확인 순서는 **세션(401) → 조직 존재(404) → 멤버 여부와 권한(403) → 대상 존재(404)** 다. 예를 들어 없는 조직은 멤버가 아니어도 404, 있는 조직의 비멤버는 403이다.
- 204 응답은 본문이 비어 있다. `response.json()`을 호출하면 실패한다.

## 4. 값의 형식

- **ID는 불투명한 문자열이다.** 해석하거나 만들지 않는다. 유저 `u:…`, 조직 `o:…`, 세션 `s:…`처럼 접두사가 붙지만 서버 내부 사정이다. 일정 ID와 초대 ID는 접두사 없는 UUID 문자열이다.
- **형식이 틀린 ID는 경로에서는 404, 본문과 쿼리에서는 400이다.** (`/orgs/garbage`는 400이 아니라 404)
- **시각:** 응답은 항상 UTC이고 밀리초가 붙는다. (`2026-11-10T03:00:00.000Z`) 요청은 `Z`로 끝나는 ISO 8601이면 되고, 밀리초는 생략해도 된다. `+09:00` 같은 오프셋은 400이다. 표시할 때 로컬 시간대로 바꾼다.
- **일정의 `title`:** 만들 때 생략하거나 빈 문자열이면 응답에서 `null`이다. 빈 제목과 제목 없음은 구분되지 않는다.
- 조직의 `description`을 생략하면 `""`가 저장된다. 응답에서는 항상 문자열이다.

## 5. 동작 규칙

### 조직과 멤버
- 조직을 만든 유저는 **관리자**가 되고, 초대로 들어온 유저는 **멤버**가 된다. `role`은 `'admin' | 'member'` 두 값뿐이다.
- 조직 삭제와 초대 보내기·취소·목록은 관리자만 가능하다(그 외는 403). 멤버 목록, 조직 정보, 일정 조회와 생성은 멤버면 된다.
- `GET /orgs/{id}`의 `memberCount`는 멤버라면 누구나 볼 수 있다.
- 탈퇴(`DELETE /orgs/{id}/members/{내 userId}`)는 본인이면 항상 가능하다. 다만 **마지막 관리자는 탈퇴할 수 없어 409**다. 다른 사람을 내보내는 것은 관리자만 가능하다.
- **탈퇴하거나 내보내지면 그 조직에서 그 유저가 만든 일정이 삭제**되고, 다른 일정의 참여자에서도 빠진다. 확인 창에서 알려주는 것이 좋다.
- 조직을 삭제하면 멤버십, 보낸 초대, 일정이 모두 사라진다. 그 조직의 초대가 다른 유저의 `/my/invites`에 남아 있다면 함께 사라진다.

### 초대
초대는 **조직 쪽 목록과 받는 유저 쪽 목록이 따로** 있어서, 한쪽의 변경이 다른 쪽에 바로 반영되지 않는다.

| 동작 | 조직 쪽(`/orgs/{id}/invites`) | 받는 쪽(`/my/invites`) |
|---|---|---|
| 보내기 | 생김 | 생김 (이미 가입한 이메일일 때) |
| 관리자가 취소 | 사라짐 | **남아 있다가**, 수락을 시도하면 409가 되고 그때 사라짐 |
| 받은 사람이 거절 | **남음**(만료까지) | 사라짐 |
| 수락 | 사라짐 | 사라짐 |

- 그래서 받는 쪽 화면은 수락 시 409(이미 처리됨)를 **"더 이상 유효하지 않은 초대"로 안내하고 목록을 새로고침**하도록 만든다.
- 거절된 초대는 조직 쪽 목록에 대기 중으로 계속 보이고, 만료 전에 같은 이메일로 다시 초대하면 409다.
- 초대 유효 기간은 7일이다. 만료된 초대는 양쪽 목록에서 빠지고, 수락하면 404다.
- **이메일 가입 여부를 알 수 없게 했다.** 가입하지 않은 이메일에 초대를 보내도 같은 201이 오고, 그 사람이 가입하면 자기 `/my/invites`에 보인다. 이미 멤버인 이메일은 409다.
- `Invite.email`은 조직 쪽 목록에서는 초대받는 이메일이고, 받는 쪽 목록에서는 내 이메일이다.
- `status` 쿼리는 값이 `'pending'` 하나뿐이고 생략해도 대기 중인 초대만 온다. `Invite`에는 상태 필드가 없다.

### 일정
- `createdBy`는 세션에서 정해진다. `participants`를 생략하면 본인 한 명이고, 조직 멤버가 아닌 유저가 있으면 400이다.
- 확정(`confirmed`) 상태로 바로 만들 수 있다.
- **상태 변경은 일정을 만든 사람이 한다.** 다른 사람의 일정은 403이고, 관리자만 예외다.
- 일정을 수정하거나 삭제하는 엔드포인트는 아직 없다. 지금은 생성, 조회, 상태 변경뿐이다.
- `from`·`to` 필터는 그 구간과 **겹치는** 일정을 돌려준다. 일정 전체가 구간 안에 있어야 하는 것이 아니다.
- 일정 목록은 필터를 생략하면 조직 전체이고 정렬을 보장하지 않는다. 화면에서 시작 시각으로 정렬한다.

### 가입
- 이메일이 이미 있으면 409다. (이메일의 대소문자는 구분하지 않는다)
- 비밀번호는 8자 이상 128자 이하이고, 가입 후 자동 로그인은 되지 않는다. 이어서 `POST /sessions`를 호출한다.

## 6. 아직 없는 것

- 역할·권한을 바꾸는 API, 비밀번호 변경, 계정 삭제, 일정 수정·삭제, 조직 정보 수정.
- 로그인 시도 횟수 제한. 목록의 페이지네이션(전체를 한 번에 돌려준다).

위 항목이 필요해지면 `shared`에 계약이 먼저 추가된다. 서버 내부에는 일부(역할 관리, 비밀번호 변경, 계정 삭제)가 이미 있다.
